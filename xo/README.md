# GigPact pact: an XO template for gig-fee escrow (Bitcoin Cash mainnet)

Template: **"GigPact pact (accepted stage)"**
Template id: `93e55492c9a7a5a9aded346e92479e67e0562815e7bfeae7b6cdbb2fdaef5996`
File: `template/gigpact-pact-template.json`
Project: GigPact, payment guarantee for live-event workers (BCH BLAZE 2026). Live app: https://gigpact-app.github.io/gigpact/ , repo: https://github.com/gigpact-app/gigpact

## What the template does

Two roles, `organizer` and `worker`. The organizer locks the gig fee in a P2SH32 "pact" output. Three spend paths:

| Action | Who signs | Output 0 must be | When |
|---|---|---|---|
| `pay` | organizer | `payoutLockingScript` (the worker) | any time |
| `waive` | worker | `refundLockingScript` (the organizer) | any time |
| `claim` | worker | `payoutLockingScript` (the worker) | only after `eventEndBlock` (CLTV) |

So the organizer can never take the fee back, the worker can never redirect it, and after the event end the worker can always collect even if the organizer disappears. Actions: `fund`, `pay`, `waive`, `claim`. Variables: `fundedSatoshis`, `payoutLockingScript`, `refundLockingScript`, `eventEndBlock`, `organizerPublicKey`, `workerPublicKey` (keys `organizerKey` / `workerKey` are generated by the engine and never leave the wallet).

## Reproduce

Node path (needs a recent Node and a funded mainnet throwaway wallet; a few thousand satoshis are enough):

```
cd scripts && npm install
# mnemonics.json: {"organizer":"<12 words>","worker":"<12 words>"}  (throwaway wallets only)
node --test vm.test.mjs                       # offline VM test of all three paths
NET=mainnet node step2.mjs organizer          # terminal 1: prints an address, fund it, builds the fund invitation
NET=mainnet node step2.mjs worker             # terminal 2: joins as worker
NET=mainnet ACTION=pay node step3.mjs organizer   # spend the pact (pay); ACTION=waive|claim with the worker
```

Browser path (blaze.xo.cash, two accounts on mainnet):
1. Both accounts: Templates, Import Template, paste `template/gigpact-pact-template.json`. In Settings, Defaults set Receive, Change and Address to Wallet (P2PKH).
2. Organizer: Create Invitation, template "GigPact pact", action Fund. Provide fundedSatoshis, payoutLockingScript, refundLockingScript, eventEndBlock, generate the organizer key. Copy invitation.
3. Worker (private window, same template imported): Join Invitation, role Worker, supply the worker public key, Update the invitation, send it back.
4. Organizer: Update invitation, Select coins (a wallet UTXO), Sign (Generate unlocking bytecode), Create transaction with "Also broadcast".
5. Paste the txid into Inspect Transaction (mainnet).

## Honest notes and known limits

* The template's `defaults.change` and the `changeOutput` slot point at the pact locking script. In the browser tool that locked the change output into the pact and the change field was read-only, so the browser fund tx was broadcast without change (the 3000 sat difference between the 5000 sat input and the 2000 sat pact output was paid as fee). In Node the change was added explicitly with `addChangeToInvitation`. A v2 of the template should drop that default. It was not changed here because editing a template changes its template id and would orphan the open invitations.
* The debug tool did not list the template-locked pact output under Assets or Scripts (Assets showed 0 BCH and only the Wallet P2PKH script), so the browser `pay` could not be started from the tool. `pay` was therefore demonstrated through the engine in Node and inspected in the debug tool.
* All wallets used were throwaway wallets with a few thousand satoshis. No keys or seeds are part of this package.
